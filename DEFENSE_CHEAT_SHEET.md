# Reflex: Defense Cheat Sheet (State → Context → Evidence)

## 1. Architecture Question
**Q: Why use SMS for the riders instead of a mobile app?**
*   **State:** We used SMS to ensure the system works on any phone, regardless of smartphone availability or data costs.
*   **Context:** Many riders use basic feature phones or have limited mobile data. A native app requires downloading, updating, and constant data.
*   **Evidence:** An SMS link uses less than 1KB of data, whereas a basic React Native app requires a 15MB+ download and constant background data syncing.

## 2. Trade-off Question
**Q: You mentioned WhatsApp API costs are a weakness. What happens if the retailer sends 1,000 messages a day?**
*   **State:** The cost would scale linearly, which could become expensive for high-volume shops.
*   **Context:** We accepted this trade-off because the cost of the API is directly tied to the revenue generated by successful deliveries. 
*   **Evidence:** If a delivery generates a 500 KES profit, and the WhatsApp message costs 5 KES, the ROI is 100x. The cost is justified by the business value.

## 3. Edge Case Question
**Q: What happens if the rider's phone dies right after they pick up the package?**
*   **State:** The system will show the order as "stuck" in the Picked Up state, and the dispatcher will be alerted.
*   **Context:** Because we didn't build an offline-first native app, we rely on the rider's active connection to update the status.
*   **Evidence:** Our design includes a "timeout" rule in the backend: if a status isn't updated within 2 hours, the dashboard flags it red for the dispatcher to call the rider manually.

## 4. Candor Question (The "I Don't Know" Question)
**Q: How would your database handle 10,000 concurrent deliveries happening at the exact same second?**
*   **State:** Honestly, my current single-database design would likely bottleneck and slow down under that specific load.
*   **Context:** I designed this for small to medium retailers doing 50-100 deliveries a day, not for a massive enterprise like Uber.
*   **Evidence:** To fix this, I would need to research database sharding or switch to a distributed database like Cassandra. I don't have the exact numbers on when it would break, but I know it wouldn't handle 10,000 concurrent writes efficiently.
